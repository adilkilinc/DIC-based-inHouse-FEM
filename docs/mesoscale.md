# Mesoscale — grain-resolved solver

`mesoscale/solver/fem_tri.py` is the grain-scale counterpart of the pixel
solver. Same physics, same constitutive routine, same conventions — the
difference is the discretisation and where the heterogeneity comes from.

| | Microscale | Mesoscale |
|---|---|---|
| Element | CPS4, 2x2 Gauss | CPS3, one integration point |
| Mesh | one element per DIC pixel, structured | unstructured SALOME grain mesh |
| Heterogeneity | per pixel, from the identified maps | per grain, from the segmentation |
| Typical size | 250k–560k elements | 90k elements, 244 grains |
| Newton | full | full + backtracking line search |

The line search is the one real algorithmic difference. Full Newton overshoots
on steps where the whole domain yields at once, and with CST elements that
overshoot **grows with mesh size** — clean at 1k elements, divergent at 90k.
The pixel solver was measured for the same failure and does not show it, so it
was deliberately left alone; see [Formulation](theory.md).

## Layout

```
mesoscale/
  solver/     fem_tri.py            the CPS3 solver
  runners/    meso_config.py        every path and switch, one file
              inp_io.py             mesh, per-grain tables and BCs from the .inp
              fem_meso_driver.py    solve
              fem_to_grid.py        rasterise onto the DIC pixel grid
              fem_time_history.py   pseudo-time histories
              run_all_fem.py        the in-house chain, six steps
              run_all_abaqus.py     the Abaqus chain, five steps
              check_grain_mapping.py, selftest.py, compare_*.py
  abaqus/     gen_inp_meso.py, job_submitter_meso.py, odb_extract_meso.py,
              odb_process_meso.py
  mesh/       the two shipped base meshes
```

## Quick start

Nothing runs without knowing where the data tree is. The two shipped meshes are
enough to exercise the chain:

```bash
cd mesoscale/runners
export MESO_CASES_DIR=../mesh          # the meshes shipped with the repository
export MESO_MESH_KEY=fine_no_twins     # or moderate_no_twins

python selftest.py             # ~1 min, builds a synthetic fixture, no Abaqus needed
python check_grain_mapping.py  # are the grains the same grains in both codes?
python run_all_fem.py          # in-house solve + comparison
python run_all_abaqus.py       # .inp -> solve -> export -> rasterise
```

Order does not matter: each chain skips steps whose outputs are already current,
and each comparison omits panels whose data is missing. The natural first pass
is the Abaqus chain then the FEM chain, because the ODB export gives the FEM its
frame times — see the warning in [Verification](verification.md).

`selftest.py` is the one to run first on a new machine. It builds a ~30-grain
fixture with matching segmentation, yield maps and DIC fields, runs every script
end to end, then injects a known error and checks the comparison recovers it.

## Configuration

`meso_config.py` holds every path and switch; no other script has one. Override
from the shell rather than editing it:

| Variable | Meaning |
|---|---|
| `MESO_MESH_KEY` | which case: `fine_no_twins`, `moderate_no_twins`, `fine_twins`, `moderate_twins` |
| `MESO_CASES_DIR` | where the case folders live |
| `MESO_THESIS_ROOT` | root of the full data tree (segmentation, DIC fields, grids) |
| `MESO_SRC_KEY`, `MESO_YIELD_T` | which identification source and yield threshold |
| `MESO_FORCE_INP`, `MESO_FORCE_FEM` | rebuild rather than reuse |
| `MESO_ABAQUS_CMD` | path to `abaqus.bat` |

Only the two no-twins meshes ship with the repository; see
`mesoscale/mesh/README.md`.

## Two .inp roles — do not confuse them

`<case>_base.inp`
: **Mesh only.** The single source of mesh and grain partition for *both*
  chains (`cfg.BASE_INP`). This is what ships in `mesh/`.

`<job_name>.inp`
: **Mesh plus data** — materials and boundary conditions written on top. This is
  an *output* (`cfg.JOB_INP`), regenerated by `gen_inp_meso.py`.

## One preprocessing path

`inp_io.build_problem()` derives the scaled mesh, the per-grain `*Plastic`
tables and the prescribed boundary displacements, and **both** chains call it.
The Abaqus deck and the in-house solve cannot drift apart, because there is only
one place that decides what the problem is.

Two behaviours of the original mesoscale runner are reproduced deliberately and
must not be "fixed" without regenerating the decks and re-running Abaqus:

1. Per-grain yield and $K$ are **truncated to whole MPa**, because the original
   wrote float grain means into a copy of the integer segmentation array.
2. The `*Plastic` table was built in float32, hence values like
   `153.86424255371094`. `meso_config.TABLE_FLOAT32` preserves that.

Both are confirmed correct in the sense that matters: the grain-mapping check
reproduces the existing decks exactly.

## Comparison design

- **Element for element**, matched by Abaqus label. `odb_extract_meso.py`
  exports raw per-element and per-node values (~40 MB) rather than a
  rasterised field per quantity (~1.8 GB).
- **One rasterisation routine** applied to both solvers, so the projection onto
  the DIC pixel grid cannot itself introduce a difference.
- **All domain means are area-weighted.** The mesh is finer at grain boundaries,
  so an unweighted mean silently weights by triangle count.

Results are in [Verification](verification.md).
